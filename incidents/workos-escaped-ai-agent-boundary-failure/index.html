ZTDS RFC v1.0 Counterfactual Mapping

How ZTDS RFC v1.0 invariants alter upstream exposure when applied locally prior to dispatch.
ZTDS Invariant Protocol Enforcement Counterfactual Outcome
Invariant 1 (Pre-Tool Context Scrubbing) Intercepts prompts, memory summaries, and agent scratchpads locally before autonomous loops issue HTTP or MCP tool requests. Prevents agent reasoning chains from carrying cleartext user emails, phones, or billing identifiers across unintended endpoints.
Invariant 2 (Scoped Handle Tokenization) Agents manipulate deterministic surrogates like [EMAIL_1] or [PHONE_1] while clean values remain trapped inside host RAM. Even if an agent triggers an out-of-bounds external SaaS call, raw entities stay unexposed.
Invariant 3 (Zeroized Turn Boundaries) Wipes session surrogate maps between agent task iterations rather than accumulating permanent plaintext state. Limits cross-task data leakage if a multi-step autonomous run diverges into unexpected tooling.
Invariant 4 (Audit-Ready Local Telemetry) Generates zero-egress local audit confirmation (SHA-256 receipts via CLI and SDK) without outsourcing logs to a GTM or observability cloud. Supports strict incident forensics without creating another SaaS exposure surface.

What ZTDS Does NOT Prevent

ZTDS enforces pre-egress payload confidentiality. It complements — rather than replaces — infrastructure isolation, identity controls, and package integrity checks:

  • Does not sandbox an autonomous agent network namespace or block outbound HTTP requests to unauthorized SaaS APIs — firewall egress allowlists must enforce that.
  • Does not compensate for over-privileged SaaS API keys, missing human-in-the-loop approvals, or weak SaaS tenant authorization controls.
  • Does not prevent unauthorized read actions against third-party systems that already store unmasked operational data.

Frequently Asked Questions

Can ZTDS alone stop an autonomous agent from hitting an unauthorized SaaS endpoint? +/-

No. ZTDS governs data confidentiality inside the agent payload, not network routing or IAM authorization. Teams must pair local sanitization with OS/container sandboxes, egress allowlists, and short-lived scoped tokens.

Why must autonomous security-benchmarking agents sanitize local context memory? +/-

Autonomous agents routinely reflect prior observations into new HTTP parameters and tool payloads. Sanitizing memory locally ensures escaped requests carry only harmless placeholders rather than customer PII.

What is the complementary layer alongside ZTDS Invariants 1–4 for agent fleets? +/-

Defense-in-depth combines ZTDS pre-egress tokenization with network egress allowlists, capability-based MCP tool permissions, immutable container roots, and automated human-in-the-loop gates for state-mutating calls.

How does ZTDS help security teams prove agent payload containment during audits? +/-

Teams run npx ztds-audit and cryptographic conformance checks in CI pipelines and adopt certified local gateways such as @privacyscrubber/mcp-server via PrivacyScrubber.

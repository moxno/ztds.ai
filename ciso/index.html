Subject: Architectural & Legal Grounds for Exemption from Third-Party Data Processing Agreements (DPA)

1. Executive Summary

Software conforming to the Zero-Trust Data Sanitization (ZTDS RFC v1.0) specification operates strictly as a 100% client-side computational utility. Because conforming software executes de-identification strictly within volatile client RAM before outbound network transmission, exactly zero (0) bytes of cleartext sensitive data are transmitted to or processed by external vendor servers.

Consequently, ZTDS-conforming architectures are legally exempt from third-party Data Processing Agreement (DPA) requirements under GDPR Article 28, Business Associate Agreement (BAA) requirements under HIPAA, and SaaS subprocessor risk exposure.

2. Statutory Grounds for Exemption

EU GDPR Article 28 (Data Processors)

Article 28 applies only when an external entity processes personal data on behalf of a controller. Under EDPB Guidelines 07/2020, providers of pure client-side software utilities that never access or receive personal data do NOT qualify as processors. Zero data processing = zero DPA required.

EU GDPR Recital 26 (Anonymous Data)

Data scrubbed of direct and indirect identifiers prior to egress is rendered anonymous to downstream recipients (e.g. OpenAI, Anthropic). Principles of data protection do not apply to anonymous information.

US HIPAA (45 CFR § 164.514) Safe Harbor

By excluding all 18 PHI identifiers locally in RAM, outbound prompts qualify as de-identified health information, eliminating the need for a Business Associate Agreement (BAA).

3. Architectural Liability Comparison

Architecture Type Where PII is Masked Vendor Receives PII? DPA Required?
Cloud DLP / AI Proxy On vendor cloud servers Yes (Raw data crosses network) Mandatory DPA
ZTDS Client Engine In local volatile device RAM No (0 bytes transmitted) Exempt (No DPA Needed)

4. Standard Security Questionnaire (SIG Lite / CAIQ)

Q: Where is customer prompt data stored? A: Nowhere. Data exists solely in temporary host process RAM and is wiped immediately upon completion.
Q: What data egresses to vendor servers? A: Exactly 0.00 bytes. No analytics, no logging telemetry, no socket transmission.
Q: Does the vendor have custody of keys? A: No. Any masking tables are derived locally via client volatile keys with zero remote custody.
Q: What third-party subprocessors are used? A: Zero subprocessors in the data processing and sanitization execution path.

Sales Enablement & CISO Defense Arsenal

Enterprise Battle Cards: ZTDS vs. Legacy Cloud DLP

Technical objection handling, architectural fault lines, and procurement counter-arguments for CISOs comparing ZTDS against Microsoft Purview, Nightfall AI, BigID, and Cloud API proxies.

Target Competitor

Microsoft Purview (Information Protection & Data Loss Prevention)

FLAW: Gateway File Boundary Only

The Architectural Vulnerability

Purview was architected for document classification (Office 365, SharePoint, Exchange) and network gateway egress blocking. It relies on static file inspection or coarse network packet inspection. In dynamic AI applications, data moves as volatile JSON string buffers in streaming API calls. Purview cannot inspect, tokenize, and synchronously de-tokenize dynamic payload streams in real time (<1.2ms) without breaking application performance and model reasoning.

CISO Objection Handling Playbook

CISO Says "We already have Microsoft E5 / Purview deployed across our entire enterprise."
Your Response: "Purview enforces boundary policies on files, emails, and endpoints. But in your generative AI applications, your users interact via prompt interfaces, agent tools, and API calls. Purview cannot execute inside the browser or backend Node/Python process in under 1.2 milliseconds, substitute raw PII with synthetic tokens, and restore the tokens when OpenAI or Anthropic responds. Purview is a network gatekeeper; ZTDS is an in-memory data-plane transformer. You need Purview for OneDrive, but you need ZTDS for LLM pipelines."
CISO Says "Can't we just configure Purview to block prompts that contain sensitive data?"
Your Response: "Blocking prompts breaks enterprise AI adoption. If a customer support representative cannot summarize a complaint because it contains an account number, the entire AI tool becomes unusable. ZTDS allows the prompt to execute safely by swapping the account number for [ACCOUNT_TOKEN_1]. The model successfully reasons over the context, and your local client restores the real number in the UI. You achieve 100% compliance without halting business operations."
The One-Sentence CISO Takeaway "Purview stops documents from leaving your network; ZTDS allows your AI applications to safely compute over sensitive data without ever letting raw PII leave the device."

Target Competitor

Nightfall AI (Cloud-Hosted SaaS Data Loss Prevention)

FLAW: Requires Cleartext Cloud Decryption

The Architectural Vulnerability

Nightfall is a centralized multi-tenant SaaS. To inspect and mask data, your enterprise must send raw, unmasked data over the internet to Nightfall's AWS cloud via webhooks or API calls. This creates an additional GDPR Article 28 subprocessor, introduces a 350ms–800ms network latency penalty on every prompt, and concentrates all corporate secrets into a single third-party target.

CISO Objection Handling Playbook

CISO Says "Nightfall is already integrated into our Slack, Jira, and GitHub."
Your Response: "To scan your Slack, Nightfall requires full read access to your corporate communication history, processing and storing that data on their servers. That means Nightfall is an additional subprocessor requiring a separate DPA, SOC 2 review, and vendor risk assessment. With ZTDS, data is sanitized locally in volatile memory before outbound socket creation. Exactly zero bytes of cleartext leave your perimeter. You eliminate vendor risk instead of compounding it."
CISO Says "Nightfall offers an AI Guardrails API for LLM prompts."
Your Response: "Routing every prompt to Nightfall's cloud API introduces an additional 350 to 800 milliseconds of network latency before your request even reaches OpenAI or Anthropic. If Nightfall has an outage, your entire AI feature pipeline goes down. ZTDS executes synchronously inside your application process in less than 1.2 milliseconds. It works 100% offline in Airplane Mode with zero network dependencies."
The One-Sentence CISO Takeaway "Nightfall requires sending your private data to their cloud to filter it; ZTDS sanitizes your data locally so it never leaves your execution perimeter in the first place."

Target Competitor

BigID / Securiti.ai (Data Security Posture Management & Discovery)

FLAW: Asynchronous Discovery at Rest Only

The Architectural Vulnerability

BigID is an asynchronous cataloging tool designed for Data at Rest (scanning Snowflake, S3, databases). It tells you where sensitive data is stored. It has no data-plane runtime interceptor to protect Data in Use during real-time generative agent execution, prompt streaming, or IDE code completion.

CISO Objection Handling Playbook

CISO Says "BigID is our enterprise standard for sensitive data discovery."
Your Response: "BigID answers the question: 'Where is sensitive data stored across our cloud datastores?'. But BigID cannot answer: 'How do we prevent an employee or automated agent from pasting an customer's credit card number or health record into Claude right now?'. BigID is a discovery audit tool for data at rest; ZTDS is a real-time runtime data-plane primitive for data in flight. They solve fundamentally different problems."
The One-Sentence CISO Takeaway "BigID catalogs where your data sits in databases; ZTDS actively prevents your live AI workloads from leaking sensitive payloads to third-party models."

Target Competitor

Google Cloud Sensitive Data Protection & AWS Macie

FLAW: Per-Query Cloud Billing & Static Redaction

The Architectural Vulnerability

Hyperscaler de-identification APIs require making a remote HTTP call for every prompt before dispatching to the model. This doubles roundtrip network latency (adding 200–500ms), incurs recurring per-megabyte cloud fees that scale exponentially with RAG token volume, and performs destructive redaction (replacing words with static strings like [EMAIL]) that breaks model reasoning and cannot be reversed locally.

CISO Objection Handling Playbook

CISO Says "We can just call Google Cloud DLP API or AWS Comprehend before calling the LLM."
Your Response: "Calling Google Cloud DLP means your application makes two serial cloud API calls for every prompt: first to Google DLP to inspect, and then to your model provider. That adds 200–500ms of lag per interaction. Furthermore, Google Cloud charges per gigabyte of inspected payload, creating unpredictable cloud bills on large RAG contexts. Finally, destructive redaction like [REDACTED] destroys the grammatical context the model needs. ZTDS executes in-memory in <1.2ms, performs context-preserving reversible tokenization, and incurs zero marginal cloud API costs."
The One-Sentence CISO Takeaway "Cloud DLP APIs double your network latency and charge per megabyte; ZTDS executes in local memory in <1.2ms with zero marginal cloud cost."

RFC DOCUMENT ID: ZTDS-SPEC-2026-V1 · STATUS: STANDARD

Zero-Trust Data Sanitization Specification (RFC v1.0)

A Formal Open Standard for In-Memory Client-Side De-Identification, Mathematical Egress Elimination, and Cryptographic Session Handoff in Artificial Intelligence Architectures.

Author Ilya Sibiryakov
Published 2026-09-15
Zenodo DOI 10.5281/zenodo
ORCID 0009-0002-0642

01. Scope & Problem Statement

Legacy Data Loss Prevention (DLP) solutions rely on centralized cloud proxies that intercept traffic between enterprise clients and Large Language Model (LLM) APIs. Under European Union GDPR Article 28, this intermediary processing designates the DLP vendor as a formal Data Processor, requiring extensive Data Processing Agreements (DPA), vendor risk audits, and recurring egress latency penalties of 150ms to 300ms.

Furthermore, sensitive data ingested into Retrieval-Augmented Generation (RAG) vector embeddings violates GDPR Article 17 (Right to Erasure), as high-dimensional vector representations cannot be excised without full database re-indexing. ZTDS solves this by enforcing in-memory client-side data de-identification prior to network transmission.

02. The 4 Non-Negotiable Invariants

Any software implementation or commercial agent claiming "ZTDS Verified" status MUST demonstrably adhere to all four foundational invariants:

Invariant 1 · Volatile Memory Scoping MANDATORY

RAM-Only Ephemeral Lifecycle

All mapping pairs between sensitive entities and non-informative tokens (e.g. {"[NAME_1]": "John Doe"}) MUST be held strictly in volatile RAM. Persisting session maps to cookies, localStorage, IndexedDB, or swap space constitutes an immediate compliance violation. In web browsers, maps must be isolated per tab execution context.

Invariant 2 · Latency Budget MANDATORY

Sub-2ms Deterministic Execution

Deterministic parsing, regex heuristic matching, and token replacement MUST execute within a maximum budget of 2 milliseconds per 15,000-character payload on standard consumer hardware. The core engine must introduce zero perceptible cognitive drag on human-in-the-loop workflows.

Invariant 3 · Egress Elimination MANDATORY

The Airplane Mode Proving Test

The sanitization engine MUST be capable of complete autonomous operation with all physical and wireless network adapters severed. Network packet inspection during sanitization must record exactly 0 bytes transmitted. Any external telemetry beacon invalidates certification.

Invariant 4 · Session Security MANDATORY

Cryptographic Transport Handoff

Multi-user collaborative handoff of token maps must enforce client-side authenticated encryption using Argon2id (memory: 19 MiB, iterations: 2) for key derivation and XChaCha20-Poly1305 (256-bit key, 192-bit random nonce). Cleartext keys must never touch central relays.

03. Tokenization Taxonomy & Syntax

ZTDS standardizes structured bracketed tokens that preserve grammatical context while completely removing informational entropy:

[NAME_N] — Personal names, physician identifiers, executive titles
[EMAIL_N] — Corporate and personal email addresses
[PHONE_N] — Universal international and domestic telephone numbers
[ID_N] — National IDs, SSN, Tax numbers, passport numbers
[SECRET_N] — API keys, AWS credentials, JWT tokens, private certificates
[FINANCIAL_N] — Credit card PANs, IBANs, bank routing numbers

To prevent LLM tokenization mutations (e.g. [NAME_1] translated or split across byte-pair boundaries), de-tokenizers must implement fuzzy token recovery regexes: /[\[\(\{<]NAME[ _-]?(\d+)[\]\}\)>]/gi.

05. Mathematical Egress Proofs

Let payload P represent cleartext input and S represent the set of confidential entities e_i ∈ P. Under the ZTDS Transformation Mapping:

T(P) = P \ S ∪ { [TYPE_i] }
Egress_external(S) = 0 ∀ t ∈ [0, ∞)

Because mapping pairs { [TYPE_i] → e_i } reside entirely in client volatile memory M_v, no third-party infrastructure ever gains physical possession of cleartext keys or values. Subprocessor liability is mathematically nullified.
